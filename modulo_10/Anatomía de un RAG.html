Anatomía de un RAG

Anatomía de un RAG

El viaje de un dato, de punta a punta: qué estructura tiene en cada paso, qué corre en Postgres y qué string exacto termina recibiendo el modelo. Todo sobre la tabla entradas de Bitácora.

Empecemos por qué es

RAG no es una tecnología, ni una librería, ni un servicio que contratás. Es el nombre de un patrón de tres pasos, y se programa con piezas que ya sabés usar. Si lo estuviste buscando como si fuera un componente, ese es el motivo por el que no aparecía.

RRetrievalRecuperación — buscás en tus datos
AAugmentedAumentada — con eso mejorás el prompt
GGenerationGeneración — y el modelo responde

La sigla se lee al revés de como sucede: primero recuperás, y eso aumenta la generación. Por eso el orden de las letras confunde.

La analogía que más sirve: un examen a libro abierto. Un modelo sin RAG rinde de memoria — contesta con lo que quedó de su entrenamiento, y si no sabe, completa. Con RAG le pasás las tres páginas del apunte que hablan del tema y le pedís que conteste mirándolas.

Sin RAG

¿qué hay que rehacer de la paleta?

la pregunta → el modelo

"Para rehacer una paleta conviene revisar el contraste, definir un color primario…"

Contesta cualquier cosa razonable. No conoce tus datos: tus entradas nunca estuvieron en su entrenamiento.

Con RAG

¿qué hay que rehacer de la paleta?

la pregunta → buscás 3 entradas → el modelo

"Los colores de la home: Laura los pidió [1] y marca dijo que el azul no representa [3]."

Mismo modelo, misma pregunta. Lo único que cambió es que antes de preguntar buscaste.

De qué se compone

Tres pasos, y ninguna pieza es nueva. La de la derecha ya la escribiste en el módulo 8; la del medio es un template string; la de la izquierda es una consulta a tu base.

Dónde encajan los embeddings y el chunking

Acá está la confusión que hace que no cierre: los tres no están al mismo nivel. El chunking y los embeddings viven adentro del paso 1, y son una forma de buscar mejor — no son el RAG.

Los pasos 2 y 3 no tienen ramas: pegar es pegar, y preguntar es la llamada de siempre. Toda la ingeniería del RAG está en el paso 1.

El RAG más simple que existe no usa embeddings

Esto termina de probar que es un patrón y no una tecnología. Acá hay un RAG completo, funcionando, con un LIKE de SQL:

// 1 · BUSCAR
const { data: entradas } = await supabase
  .from("entradas").select("titulo, texto")
  .ilike("texto", `%${palabraClave}%`).limit(5);

// 2 · PEGAR
const contexto = entradas.map(e => `${e.titulo}\n${e.texto}`).join("\n\n");

// 3 · PREGUNTAR
await ai.models.generateContent({
  contents: `Entradas:\n${contexto}\n\nPregunta: ${pregunta}`
});

Nueve líneas, cero embeddings, cero pgvector. Eso ya es un RAG. Funciona, y falla en un solo caso: si la entrada dice "cambiar los colores" y preguntás por "la paleta", el LIKE no encuentra nada.

Los embeddings existen para arreglar exactamente ese caso. Son una mejora del paso 1, no un requisito del patrón.

Lo primero: son dos programas distintos

La confusión más común es pensar el RAG como un solo flujo. Son dos, corren en momentos distintos y se tocan en un solo lugar: la columna embedding.

Indexación

Corre una vez por entrada, cuando el usuario guarda. Convierte texto en vector y lo escribe en la fila.

Consulta

Corre en cada pregunta. Convierte la pregunta en vector, busca las filas más cercanas y arma el prompt.

1.2

¿Hace falta chunking?

Chunking es partir un texto largo en fragmentos antes de embeberlo. La decisión se toma acá y depende de una sola cosa: cuántos temas distintos tiene el texto.

Bitácora — no 
texto: 312 caracteres
temas: 1
─────────────────────
→ 1 fragmento = la entrada
Un PDF de 40 páginas — sí 
texto: 98.400 caracteres
temas: ~25
─────────────────────
→ ~40 fragmentos de 200-500
  palabras, cortados por
  sección

La regla que decide dónde cortar: cada fragmento tiene que entenderse solo. Si un fragmento dice "esto hay que cambiarlo" sin decir qué, es inútil recuperado fuera de contexto.

1.3

El texto se convierte en vector

Una llamada a la API de embeddings. No es una llamada a un LLM: no genera texto, no razona, no tiene prompt. Entra un string, sale un array de números de largo fijo.

La llamada 
const r = await ai.models.embedContent({
  model: "gemini-embedding-2",
  contents: texto,
  config: { outputDimensionality: 768 }   // ← tiene que coincidir con vector(768)
});
const vector = r.embeddings[0].values;
Lo que vuelve 
[
   0.0231, -0.0847,  0.1124, -0.0392,  0.0663,
  -0.0158,  0.0977, -0.0541,  0.0289, -0.1003,
  … 758 números más
]
length: 768   ·   cada valor entre -1 y 1

Ese array no es un resumen. No se puede volver a convertir en texto, no hay una dimensión que signifique "colores" ni otra que signifique "Laura". Es una coordenada: su único uso es medir distancia contra otras coordenadas del mismo espacio.

1.4

El vector se guarda en la fila

No hay base de datos aparte. El vector es una columna más de la misma tabla, al lado del texto que lo originó.

DDL 
create extension if not exists vector;

alter table entradas add column embedding vector(768);

El texto y su vector viven juntos. Por eso la búsqueda puede devolver el contenido original sin un segundo viaje, y por eso las políticas RLS que ya escribiste siguen protegiendo todo.

2.1

La pregunta pasa por el mismo proceso

Exactamente la misma llamada del paso 1.3, con el mismo modelo y las mismas dimensiones. Si acá usaras otro modelo, estarías midiendo distancias entre puntos de dos mapas distintos.

const q = await ai.models.embedContent({
  model: "gemini-embedding-2",       // ← el mismo que en 1.3
  contents: "¿qué hay que rehacer de la paleta?",
  config: { outputDimensionality: 768 }
});
2.2

Postgres compara contra todas las filas

El operador <=> calcula la distancia coseno entre dos vectores. ORDER BY por esa distancia y LIMIT 5: eso es toda la búsqueda semántica.

create or replace function buscar_entradas(
  query_embedding vector(768),
  cantidad int default 5
)
returns table (id uuid, titulo text, texto text, similitud float)
language sql stable security invoker as $$
  select
    entradas.id,
    entradas.titulo,
    entradas.texto,
    1 - (entradas.embedding <=> query_embedding) as similitud
  from entradas
  where entradas.user_id = auth.uid()      // ← de la sesión, no del cliente
    and entradas.embedding is not null
  order by entradas.embedding <=> query_embedding
  limit cantidad;
$$;

El where user_id es la línea más importante del archivo. Sin ella la búsqueda recorre las entradas de todos los usuarios de la app. Y tiene que salir de auth.uid(), no de un parámetro: un parámetro que llega del navegador lo puede cambiar cualquiera desde la consola.

2.3

Vuelven cinco filas, ordenadas por similitud

De 200 entradas a 5. La columna similitud va de 0 a 1 y es la que te permite diagnosticar: si el primer resultado está en 0.40, la búsqueda no encontró nada bueno.

Fijate en la entrada 1: dice "cambiar los colores" y la pregunta decía "rehacer la paleta". Cero palabras en común, similitud 0.891. Eso es lo que un LIKE '%paleta%' nunca habría encontrado.

2.4

Se arma el prompt con esos cinco

Acá el RAG deja de ser matemática y vuelve a ser un string. Esto es literalmente lo que recibe el modelo:

systemInstruction 
Respondé preguntas sobre las entradas del usuario usando ÚNICAMENTE
las entradas que te paso.

- Si la respuesta no está en ellas, decí "No encontré esa información
  en tus entradas". No completes con suposiciones.
- Citá de qué entrada sacaste cada dato, con su número entre corchetes.
- Sé breve y concreto.
contents 
Entradas:

[1] 2026-09-15 · Reunión con Laura — rediseño
Laura pidió cambiar los colores de la home. Quedé en mandarle
dos propuestas el viernes.

[2] 2026-09-08 · Llamada rápida por la home
Revisamos el hero. Quedó pendiente definir la tipografía.

[3] 2026-08-29 · Feedback del equipo de marca
Dijeron que el azul actual no representa la marca.

Pregunta: ¿qué hay que rehacer de la paleta?

El modelo nunca vio tu base de datos. Vio este string. Todo lo que sabe de tus entradas en esta respuesta se lo diste vos, en esta llamada, en estos caracteres.

2.5

La respuesta vuelve con sus fuentes

Las citas no son decoración: son lo que permite verificar. Un RAG sin fuentes visibles es un generador de afirmaciones plausibles.

{
  "respuesta": "Hay que rehacer los colores de la home: Laura los pidió
                 explícitamente [1], y el equipo de marca marcó que el azul
                 actual no representa la marca [3]. Quedaste en mandar dos
                 propuestas el viernes [1].",
  "fuentes": [
    { "n": 1, "id": "3f2a9c10…", "titulo": "Reunión con Laura…", "fecha": "2026-09-15" },
    { "n": 3, "id": "a71c04ff…", "titulo": "Feedback del equipo…", "fecha": "2026-08-29" }
  ]
}

Por qué "cerca" es aritmética

Con 768 dimensiones no se puede dibujar. Con 4 sí, y la operación es exactamente la misma: coseno entre dos vectores, que da 1 cuando apuntan igual y 0 cuando no tienen nada que ver.

La pregunta
[ 0.82,  0.31, −0.12,  0.45 ]
—
Entrada A
[ 0.79,  0.28, −0.09,  0.51 ]
0.997
Entrada B
[ −0.22,  0.61,  0.77, −0.13 ]
0.048

Postgres hace esta cuenta contra cada fila que tenga embedding, ordena por el resultado y te devuelve las cinco primeras. Con cientos de filas eso son milisegundos y no necesita índice; el índice aparece cuando son cientos de miles.

Los cuatro errores de estructura

Todos producen el mismo síntoma — "no encuentra nada" o "trae cualquier cosa" — y se diagnostican en lugares distintos.

ErrorCómo se veDónde se arregla
Dimensiones distintas expected 768 dimensions, not 3072 El vector(N) y el outputDimensionality
Modelo distinto entre index y query Trae resultados sin relación, sin error Que 1.3 y 2.1 usen el mismo string de modelo
Filas sin embedding Existen en la tabla y son invisibles a la búsqueda Backfill: where embedding is null
Texto editado sin regenerar el vector La encuentra por lo que decía antes Regenerar el embedding en cada update del texto

El tercero y el cuarto son los peligrosos, porque no tiran ningún error. Un RAG con embeddings desactualizados no se rompe: responde con seguridad sobre contenido que ya no existe.
